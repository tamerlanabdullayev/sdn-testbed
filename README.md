# SDN Controller Benchmarking Testbed

An open-source testbed for benchmarking OpenFlow SDN controllers under a
reproducible, seeded TCP workload. It accompanies the paper *(ICC 2027)*; the
testbed itself is the contribution.

**Pipeline.** Mininet + Open vSwitch emulate the network; iperf3 generates TCP
flows between random host pairs at a fixed flow rate; an instrumented
controller app logs per-Packet-In handler timing and per-second
Packet-In/FlowMod counts; tcpdump captures the OpenFlow channel for
controller-independent (wire) latency; a psutil monitor logs controller CPU and
memory. `scripts/run_experiment.py` runs one experiment for any controller and
appends one row per run to `summary.csv`; `scripts/sweep.py` runs the whole
matrix.

Three controllers are included, running the same L2 learning-switch logic:
**Ryu 4.34**, **OS-Ken 2.8.1** and **ONOS 2.7.0**.

## Requirements

- Linux with root access (Mininet needs `sudo`), x86-64. The paper's data come
  from Ubuntu 24.04.2, kernel 7.0, in a 4-vCPU VirtualBox VM; exact versions
  in [`docs/ENVIRONMENT.md`](docs/ENVIRONMENT.md). The install steps below have
  not been verified on a fresh machine.
- System packages (apt): Mininet 2.3.0, Open vSwitch 3.3.4, iperf3 3.16
  (needs `--fq-rate`, Linux only), tcpdump; for ONOS also OpenJDK 11 and Maven.
- Python **3.10** for the controller virtualenvs (Ryu 4.34 is unmaintained and
  was not tested on newer Python). On Ubuntu 24.04, install it e.g. from the
  deadsnakes PPA.
- 4 CPUs for the default pinning (controller on CPU 3, workload on CPUs 0–2;
  see `--controller_cpus` / `--workload_cpus`).

Mininet and OVS run with the system `/usr/bin/python3` under sudo; the
controllers, the monitor, the aggregator and the plotting scripts run in the
virtualenvs.

## Install

```bash
# 1. System packages
sudo apt install mininet openvswitch-switch iperf3 tcpdump

# 2. Ryu virtualenv (the scripts expect it at ./venv_py310, fallback ./venv)
python3.10 -m venv venv_py310
source venv_py310/bin/activate
pip install --upgrade pip
pip install -r requirements.txt          # pinned versions used for the paper

# 3. Ryu 4.34 from source, with the patches needed on current setuptools/eventlet
#    (still inside venv_py310; the source tree is gitignored)
wget https://github.com/osrg/ryu/archive/refs/tags/v4.34.tar.gz
tar -xzf v4.34.tar.gz                    # creates ryu-4.34/
cd ryu-4.34
sed -i '27d' setup.py                    # remove the setuptools hook ...
sed -i '/import ryu.hooks/d' setup.py    # ... and its import
sed -i '109,112d' ryu/app/wsgi.py        # drop the ALREADY_HANDLED dependency
sed -i '109i\class _AlreadyHandledResponse(Response):\n    pass' ryu/app/wsgi.py
pip install --no-deps -e .               # dependencies are pinned in requirements.txt
cd ..
ryu-manager --version                    # should print 4.34
deactivate

# 4. OS-Ken virtualenv: same Python 3.10 / eventlet as Ryu
python3.10 -m venv venv_osken_py310
venv_osken_py310/bin/pip install -r requirements-osken.txt

# 5. ONOS 2.7.0 + the instrumented app (optional; only for ONOS runs)
sudo apt install openjdk-11-jdk-headless maven
scripts/setup_onos.sh                    # see docs/ADAPTER.md Part 4
```

Ryu is an **editable** install (`pip install -e`): the venv imports Ryu from
the extracted `ryu-4.34/` source tree, so that folder must stay where it was
when you installed it (moving or deleting it breaks Ryu; reinstall with
`pip install --no-deps -e <new path>`). `venv_py310/bin/pip show ryu` prints
its location ("Editable project location"). Do not name the source tree
`ryu/` inside the repository: with the repository root as the working
directory, Python would import that folder instead of the package.

The run scripts call `sudo` several times per run (Mininet, `mn -c`, `pkill`,
`chown`, tcpdump). For unattended sweeps, configure passwordless sudo for
those commands or keep the sudo timestamp fresh (e.g.
`sudo -v; while true; do sudo -n -v; sleep 60; done &`): a sweep stops at the
first password prompt.

## One run

```bash
venv_py310/bin/python scripts/run_experiment.py --controller ryu --n 4 \
    --run_id SMOKE_STAR_N4_F200 --fps 200 --total_time 20 --flow_duration 2 --seed 1241 --topo star

# the same with the positional wrapper:
# scripts/run_experiment.sh N RUN_ID FPS TOTAL_TIME FLOW_DURATION SEED TOPO
CONTROLLER=osken scripts/run_experiment.sh 4 SMOKE_STAR_N4_F200 200 20 2 1241 star
```

- `--controller` / `CONTROLLER`: `ryu`, `osken` or `onos`.
- `TOPO`: `star`, `tree` (alias `fattree`; recorded as `fattree` in the data),
  or `mesh` (experimental, see Known limitations).
- Environment variables (defaults are the single-run defaults; `sweep.py`
  sets the paper's pinning and warm-up):
  - `FQ_RATE=2M`: per-flow iperf3 `--fq-rate` pacing (`0` = unpaced).
  - `HOST_BW=0`: Mbit/s tc limit on host–switch links (`0` = none).
  - `CAPTURE=1`: OpenFlow capture and wire metrics (`0` skips them).
  - `CONTROLLER_CPUS` / `WORKLOAD_CPUS`: CPU pinning, e.g. `3` / `0-2`
    (default none).
  - `WARMUP_ROUNDS` / `WARMUP_HOSTS`: warm-up networks before the measured
    one (default 0 / 16). See `docs/ADAPTER.md` §2.7.
  - `RESULTS_ROOT` (default `results_v4`), `READY_TIMEOUT` (s, default 120),
    `RYU_PYTHON` / `OSKEN_PYTHON` (controller interpreter, `docs/ADAPTER.md`
    §2.6); ONOS: `ONOS_HOME`, `ONOS_JAVA_HOME`, `ONOS_HEAP` (§4.3).
  - `KEEP_PCAP=1`, `KEEP_IPERF_JSON=1`, `KEEP_LOGS=1` keep the capture, the
    per-flow iperf3 JSONs and the controller/Mininet/warm-up logs, which are
    otherwise deleted after a successful aggregation.
- Output: `<RESULTS_ROOT>/raw/<controller>/<RUN_ID>/`, and one row appended to
  `<RESULTS_ROOT>/summary/summary.csv` (shared by all controllers).
  Prefix trial run IDs with `SMOKE` (the plotting scripts skip such rows).
- A run takes about 35 s wall clock (ONOS about 75 s, most of it ONOS
  start-up); the per-phase breakdown is printed at the end and saved in
  `phase_times.json`.

## Smoke test

```bash
venv_py310/bin/python scripts/sweep.py --smoke --results_root results_smoke
# other cases: CASES="ryu:star:64 osken:star:64 onos:tree:64" (controller:topology:N, 200 fps)
```

Runs a few worst-case runs with the sweep's settings and prints `[SMOKE] GO`
or `NO-GO` (success rate ≥ 0.98, controller and system CSVs non-empty, all
summary columns filled).

## Full sweep (as in the paper)

N = 4, 8, 16, 32, 64 hosts × FPS = 25, 50, 100, 200 flows/s × 10 repetitions
× star and tree, 20 s runs, 2 s flows, seed = B_T + 10N + FPS + rep
(B_T = 1000 star, 2000 tree): 400 runs per controller, 1200 in total.
Controller pinned to CPU 3, workload to CPUs 0–2, one warm-up round.

```bash
tmux new -s sweep
venv_py310/bin/python scripts/sweep.py --dry_run          # list the runs and the estimated time
venv_py310/bin/python scripts/sweep.py 2>&1 | tee "sweep_$(date +%F_%H%M).log"
# subsets: --controllers ryu --topos star --hosts 4,8 --fps 200 --reps 2
```

- Order: controller (ryu → osken → onos) → topology → N → FPS → rep.
- Runs already in the summary are skipped, so an interrupted sweep continues
  with the same command; a failed run is logged and the sweep goes on (rerun
  the command to retry it).
- Each sweep writes `<results_root>/sweeps/sweep_<time>.json`: parameters,
  machine and software environment, code hash, and the exit code and wall
  time of every run. `sweep.py` warns if the code hash changes mid-sweep.
- Never run two sweeps (or a sweep and a single run) at the same time: every
  run starts with `sudo mn -c`, kills leftover controllers, and uses OpenFlow
  port 6653.
- Duration: about 16 h for all 1200 runs (Ryu and OS-Ken about 3.8 h each,
  ONOS about 8.2 h).

## Metric definitions

- **Workload facts (not bugs, but must stay documented):** flow entries have no
  idle/hard timeout and ARP is static, so Packet-Ins occur only on first
  contact per directed MAC pair per switch; controller load is bounded by unique
  pairs, not FPS.
- **Latency metric definition:** `proc_time_ms` is measured from Packet-In
  *handler entry* to after the response is sent (FlowMod+PacketOut, or flooding
  PacketOut). It excludes event-queue wait. Flood events are included.

  More precisely, "sent" means the last send call has returned, i.e. the
  message was handed to the framework (serialized and queued on the datapath's
  send queue in Ryu/OS-Ken; handed to ONOS's flow and packet subsystems in
  ONOS); the socket write is not included. Values are milliseconds.

- **Wire response time** (`wire_*`, controller-independent;
  `analysis/openflow_latency.py`):
  - *Capture:* `tcpdump -i lo tcp port 6653` with nanosecond kernel
    timestamps, pinned to the workload CPUs. It starts after the controller is
    ready and after warm-up, and stops after the Mininet network is stopped,
    before the controller is stopped.
  - *Reassembly:* each TCP direction is reassembled in sequence order and split
    into OpenFlow 1.3 messages; a message's time is the capture time of the
    TCP segment that completes it.
  - *Matching* (no xid; `buffer_id` is always `NO_BUFFER` because the
    table-miss rule uses `OFPCML_NO_BUFFER`): per switch connection, a
    PacketOut matches the Packet-In with *identical packet bytes*, and a
    priority > 0 FlowMod matches the Packet-In with the same `in_port`,
    `eth_src`, `eth_dst`; identical duplicates are paired first-in-first-out.
    A flooding PacketOut completes its event (no FlowMod follows).
  - *Timer:* starts at the Packet-In; `wire_last_ms` stops at the later of
    the matched PacketOut and FlowMod (the controller has sent its whole
    response), `wire_first_ms` at the earlier. A Packet-In with no matched
    PacketOut is `unmatched` and has no latency.
  - *Scope:* every Packet-In in the capture, flood events included;
    `wire_clean_*` also drops ambiguous events (see the summary table).
  - *Includes* the controller's socket read, parsing, event-queue wait,
    handler and socket write, plus the loopback TCP stack, so
    `wire_last_ms ≥ proc_time_ms`; under load the difference is dominated by
    queueing. *Excludes* time inside OVS before the Packet-In is written and
    the time the switch takes to apply the FlowMod.
  - Disable with `CAPTURE=0`.
- **Packet-In counts vary between runs.** Packet-Ins are not limited to the
  first packet per pair: packets arriving before the FlowMod is installed cause
  repeat Packet-Ins (more for a slower controller), and hosts send IPv6 ND/MLD
  multicast on their own schedule. Raw Packet-In counts therefore vary between
  runs with the same seed. On star the set of unique unicast `(dpid, src, dst)`
  does not; on the tree it depends on timing too (when a MAC is learned on each
  switch decides between a FlowMod and a flood), so it differs between runs,
  even between Ryu and OS-Ken.
- **Controller CPU:** psutil `cpu_percent` of the controller PID, sampled every
  1 s by a separate process (one interval after start, so there is no
  zero-length first sample); % of one core. When a warm-up ran, samples
  before `measure_start_ts` (controller start-up and warm-up) are dropped.
- **Percentiles** use `v[min(int(len(v)*q), len(v)-1)]` on the sorted values.

### ONOS-specific behaviour

ONOS runs the same forwarding logic (`docs/ADAPTER.md` Part 4), but its
OpenFlow traffic differs in ways that are inherent to ONOS:

- **No link discovery.** Only `drivers`, `openflow-base` (with its dependency
  `optical-model`) and the testbed app are active; the LLDP/BDDP link
  providers and the host provider are not. None of the 1200 runs in
  `results_v4` has an LLDP, BDDP, broadcast or ARP Packet-In: every Packet-In
  destination, on the wire and in the controllers' logs, is a unicast host MAC
  or IPv6 multicast (`33:33:…`).
- **FLOW_REMOVED at teardown.** ONOS sets `OFPFF_SEND_FLOW_REM` on its
  FlowMods, so OVS sends FLOW_REMOVED messages when the switches are deleted
  at the end of a run (158 of the 400 ONOS runs in `results_v4` captured
  them; Ryu and OS-Ken have none). Rules are not removed during traffic.
- **PacketOut sometimes before FlowMod.** ONOS's flow subsystem sends each
  FlowMod (followed by a BarrierRequest) on its own thread, so the FlowMod may
  leave after the PacketOut, and some rules are re-sent. The wire matcher
  handles both orders; re-sent FlowMods with no waiting Packet-In are counted
  as `unmatched_flow_mod` in `wire_summary.json`.
- `proc_time_ms` ends when ONOS has accepted the FlowMod and PacketOut into its
  own queues, so it covers less of the controller's work than in Ryu/OS-Ken:
  compare ONOS with the other controllers using `wire_*`, not `proc_*`.

## Adding a topology

1. Create `topology/<name>_topo.py` with a Mininet `Topo` subclass whose
   `build(self, n)` creates hosts named **`h1` … `hN`** (the traffic generator
   relies on these names) and switches named `s<number>`.
2. Register it in `get_topo()` in `scripts/run_mininet_iperf.py` (add an alias
   to `TOPO_ALIASES` if needed).
3. For sweeps, add it to `SEED_BASE` and `RUN_PREFIX` in `scripts/sweep.py`
   with its own seed base `B_T` (1000 star, 2000 tree and 3000 mesh are
   taken), then run `scripts/sweep.py --topos <name>`.

Topologies with loops need a controller with loop prevention (see mesh below).

## Adding a controller

The contract — forwarding logic, timing points, CSV schemas, `OUTDIR`, the
cooperative per-second logger, and the adapter lifecycle (start, PID,
readiness, stop) — is in [`docs/ADAPTER.md`](docs/ADAPTER.md). The three
included controllers are the examples:

- **Ryu** and **OS-Ken** (Python): `controller/*_instrumented_switch.py` and
  `controller/adapters/python_managers.py`; `docs/ADAPTER.md` Part 3 walks
  through the Ryu → OS-Ken port.
- **ONOS** (Java, OSGi app + REST readiness check):
  `controller/onos-instrumented-l2/`, `controller/adapters/onos.py`,
  `scripts/setup_onos.sh`; `docs/ADAPTER.md` Part 4.

A controller is added by writing the app, subclassing `ControllerAdapter` in
`controller/adapters/` and registering it in `ADAPTERS`; it is then selected
with `--controller <name>` / `CONTROLLER=<name>`. For sweeps, add the name to
`CONTROLLERS` (and a rough per-run time to `EST_S`) in `scripts/sweep.py`.
Check it with a smoke test (`docs/ADAPTER.md` §3.4).

## Known limitations

- **Packet-In load is bounded by unique directed host pairs**, not by flow
  rate, because flow entries are permanent and ARP is static (see Metric
  definitions).
- **Handler time** excludes event-queue wait and the socket write, and covers
  different amounts of work per framework (see ONOS-specific behaviour); use
  the wire metrics to compare controllers.
- **"Tree" is a two-tier tree**, not a k-ary fat-tree: 1 core switch,
  ceil(N/4) edge switches, ≤ 4 hosts each, no redundant paths. Edge switches
  have dpids 1..16, the core 1000.
- **Mesh is experimental**: it has loops and the reference controller has no
  STP, so flooded broadcasts cause storms. It is not part of the published
  results.
- **`delivered_throughput_bps` overstates the delivered rate.** In
  `results_v4` it is ≈1.29× (Ryu, OS-Ken) and ≈1.22× (ONOS) the nominal paced
  load (FPS × 2 s × 2 Mbit/s / 2 s). It is computed from iperf3's sender-side
  `end.sum_sent.bytes`, which counts bytes *written to the socket*, including
  data still in the send buffer when the test ends — not bytes delivered.
  A verification run (star, N = 4, 200 fps, `KEEP_IPERF_JSON=1`) showed per
  flow 655,360 B sent and 393,216 B received against a nominal 500,000 B
  (2 Mbit/s × 2 s). Both counters move in whole 128 KiB iperf3 blocks, which
  is coarse for a 500 KB flow; the delivered volume lies between the two.
  `end.sum_received.bytes` (a lower bound) is the more accurate field.
  `total_throughput_bps` is a legacy sum of per-flow rates and is not
  aggregate throughput either.
- **Single machine**: traffic generators, switches, controller and monitor share
  one (virtual) machine; pinning separates the controller from the workload,
  but `ovs-vswitchd` and the kernel datapath are not pinned.
- **ONOS start-up** takes about 24 s per run (fresh Karaf data each run) and
  occasionally fails (2 of 402 attempts in the v4 sweep); a failed start
  produces no summary row and is retried by rerunning the sweep.
- **Port reuse**: the iperf3 server pool is sized for < 0.01% port collisions;
  `results_v4` has 49 (Ryu), 49 (OS-Ken) and 46 (ONOS) out of 750,000 flows
  each, all recorded in `port_collisions`.
